# Tech summary spec — input to build.py
`<skill>` = this skill's folder. Run from the repo root:
`python <skill>/references/templates/build.py generated-docs/_spec/tech-summary.json generated-docs/tech-summary.html [--md generated-docs/tech-summary.md]`
- Prints WARN lines, a summary line (components · flows · entities · integrations · risks · reading time), then `built <outs>: 11 sections, N WARN (templates <ver>)`. ERROR lines stop the build.
- Writes the generator tag (`darshan-singh-meel-docs-tech-summary <ver>`), the `.generated-by-darshan-singh-meel-docs` marker in each output folder (the knowledge graph skips it), and the Markdown first line `<!-- generated by darshan-singh-meel-docs-tech-summary <ver> -->`.
- Run from a repo root (a `.git` folder present): every repo path in `where`, `pinned_in` and `go` must exist (WARN).
- Start from `examples/tech-summary-example.json`; nothing of the example survives. Tests: `python <skill>/tests/run.py`.
- Helpers: `stack.py [repo_root]` lists pinned versions (`tech | version | file`) from manifest and pin files only (incl. conda `environment.yml`); `shots.py <html> <shots_dir>` renders at 1280 and 390 px and prints `LAYOUT` lines (also text outside a diagram). Markdown: Mermaid entity names quoted, a keys table under each ER diagram, `<` escaped.

## Fixed sections, free content
Same 11 sections, these names, this order, every run; the build refuses a missing or extra one. A section with nothing to say is one `line` ("No persisted data: the service is stateless."); in a core section (★) that is a WARN.

| # | Section | Required blocks | Holds | Budget (WARN over) |
|---|---|---|---|---|
| 1 | At a glance ★ | `facts`, `scope` | what · stack · runs on · schedule · in → out · owner; Does / Doesn't / Limitations | scope 1–5 each |
| 2 | Components ★ | `flow`, `components` | runtime parts with real names; one box per component (same label) | 8 components, 10 boxes |
| 3 | Main flows ★ | `seq` | the flows a new engineer meets first; each with a step table, an example where it helps | 4 flows, 7 steps, 6 participants |
| 4 | Data model | `er` | core entities, keys only, cardinality | 12 entities, 5 keys each |
| 5 | Integrations | `integrations` | external systems, direction, protocol, data, auth names | 10 |
| 6 | Tech stack ★ | `stack` | layer, tech, version as pinned, file that pins it | 15 |
| 7 | Deploy and environments | `envs` | envs, how each deploys, access; pipeline, rollback, health in bullets | 5 envs |
| 8 | Security and access | – | identity, roles, secrets (names), personal data, network | 8 bullets / 12 rows |
| 9 | Run locally ★ | `commands` | clone to running, in order, with expected output | 8 commands |
| 10 | Top risks ★ | `risks` | design and operational risks plus confirmed issues; status per row | 7 |
| 11 | Where to look next ★ | `pointers` | Technical doc sections, folders and files for the detail left out | 10 |

Also over budget: any `bullets` over 8 items · any `table` over 12 rows · facts over 8 · rules over 5 · a table with a `Default(s)` column (a config table is Technical-doc depth) · more than half of the components being single files · reading time over 15 min (prose words / 200 + 0.5 min per diagram; code and payloads not counted).

## Fields
```json
{"title": "<repo>: tech summary", "date": "YYYY-MM-DD", "subtitle": "<stack> · <runs on> · <inputs> → <outputs>",
 "commit?": "<short sha>", "graph?": "knowledge graph at <sha> | file scan",  // sha ≠ commit → WARN
 "sections": {"<fixed name>": {"line": "…"} | {"lead?": "…", "blocks?": [ … ], "subsections?": [{"title": "…", "blocks": [ … ]}]}}}
```
A section renders `lead`, its own `blocks`, then `subsections`. Subsection titles come from the repo (a service, a job); a title that fits any repo ("Overview", "Details") is a WARN.

## Blocks
| Type | Fields | Rendered as |
|---|---|---|
| `text` | `text` | paragraph |
| `bullets` | `items` | list |
| `table` | `head`, `rows`, `title?` | table |
| `facts` | `rows` [[label, value]] (≤8) | label/value grid |
| `rules` | `rows` [{rule, where: path:line}] (≤5) | list; optional, under At a glance or Main flows |
| `scope` | `does` [1–5], `doesnt` [1–5], `limits?` [≤5] | three columns: Does · Doesn't · Limitations |
| `flow` | `title`, `nodes` [{id, label, sub?, kind: actor·service·job·tool·store·external·entry, col, row, tag?}], `edges` [{from, to, label? ≤14 chars, ≤9 between neighbours in a row, dashed?}], `lanes?` (one per row), `key` | SVG boxes on a grid; one id per grid cell; ≥3 boxes |
| `seq` | `title`, `why?`, `participants` [{id, label, kind?}], `steps` [{from, to, do ≤8 words, out, where?, alt?, back?}], `example?` {in, out, source}, `key?` | sequence diagram (numbered), then `# · Step · Output · Where` table (`alt` = "If not: …"), then IN / OUT payloads |
| `er` | `title`, `entities` [{id, name, keys: ["PK id", "FK x_id", "UK y", "col"], more?: n}], `rels` [{a (one side), b, card: 1:1·1:N·N:1·N:M, on ≤14 chars, logical?}], `key` | entity cards in rows of 4; related entities next to each other (a relation that skips a row is a WARN) |
| `example` | `title`, `in`, `out`, `source` | IN / OUT payloads with the source line |
| `components` | `rows` [{name, does, tech, where, kind?}] | table; `where` a folder or module (a single file only for kind job or script) |
| `integrations` | `rows` [{system, direction: in·out·both, via, data, auth?}] | table |
| `stack` | `rows` [{layer, tech, version ("not pinned" when so), pinned_in}] | table |
| `envs` | `rows` [{env, runs_on, deploy, access}] | table |
| `commands` | `rows` [{cmd, does, expect?}] | table, command as code |
| `risks` | `rows` [{risk, impact, status: Confirmed·Not verified·Design risk·Owner to decide, mitigation, where?}] | table with status chips |
| `pointers` | `rows` [{topic, go, why?}] | table |

Text: `code` and **bold** render; ≤40 words per string (code fields excepted). Participants and diagram boxes use the names in Components or Integrations.

## Checks
**ERROR** (no output): a fixed section missing or unknown · a section with neither `line` nor blocks, or both · a required block missing · unknown block type · a typed row without its required fields · risk status, integration direction, node kind or relation card outside its list · flow box without id/label/col/row, id or grid cell twice, under 3 boxes, edge to an unknown box, fewer lanes than rows · seq with under 2 participants, a step without from/to/do/out or naming an unknown participant · example without in/out/source · ER relation to an unknown entity or without `on` · scope `does`/`doesnt` not 1–5 items · table head and rows of different length · `TODO` · absolute or machine path · an e-mail address or phone number · a rules row without `path:line` · a literal secret value (`KEY=value`, `token: value`, `user:password@`, `Bearer …`, JWT, token shapes `dapi…`, `AKIA…`, `ghp_…`, `xoxb-…`, `sk-…`; write `<redacted>`) · absolute paths include `C:\`, `/c/Users/`, `\\server\share`, `%VAR%\`, `/Workspace/Users/` · missing output folder.

**WARN**: every budget above · a one-line core section · generic subsection title · diagram without `key` (seq gets a fixed key) · edge or relation label over 14 characters · box text cut · step `do` over 8 words · participant that is no component, integration or box · component that is no box · repo path not found, or a `path:line` past the file's end · a link into the knowledge-graph folder (git-ignored) · `graph` commit ≠ `commit` (graph behind: recount from code) · chat voice (`you`, `the user`, `Claude`, `as discussed`, `confirm with`, `was skipped`, …) · filler (robust, seamless, leverage, very, simply, comprehensive, …) · a string over 40 words · the same sentence (≥6 words) twice.
