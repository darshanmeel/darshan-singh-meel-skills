description: Build, maintain, and query a detailed knowledge graph of a repo, folder, or large document set — code, calls, flows, business and dbt logic, data model, lineage, infra, documents, processes, test cases — in a git-ignored knowledge-graph folder in the repo, plus an optional system graph across related repos. Use to map a repo, to update the graph after changes, and to answer questions like what something does end to end, how a process works, which function calls which procedure, what breaks if something changes, or where something is used.

# Knowledge graph
Detailed, verifiable map. Answers, docs, reviews stand on it — wrong graph, everything wrong. Accuracy first. CLAUDE.md applies.

## Scope — mapping only
- Map what the code does. Not a code review: no bug hunting, investigating, confirming, measuring, or running the app.
- Looks wrong → `possible_issue` note on the node (one line + `path:line`), **not verified**, move on.
- Report: count + ≤5 one-liners (dead code, cycles, unused models, possible bugs) under "Noticed while mapping (not verified)" + "Run a review to check these" (`darshan-singh-meel-review`). Never "confirmed bugs", severity, impact numbers.

## 1. Setup (first build only)
Graph exists (`./<repo>-knowledge-graph/` or path in `./.knowledge-graph`) → §5 with saved settings. Else list doc files silently, then one prompt, 4 questions:
| Header | Question | Multi | Options (rec first) |
|---|---|---|---|
| Location | Where? | no | `./<repo>-knowledge-graph/`, git-ignored (rec) · same, committed · another path |
| Doc sources | Which docs to read? | yes | Hand-written: READMEs, specs, runbooks (rec) · Everything · Let me pick what to skip · Code only |
| Priority | Docs outranking code? | no | No — code is truth (rec) · Yes, I'll pick (specs, contracts, regulations) |
| Related repos | Other repos related? | no | No (rec) · Yes, I'll give paths |
- Save in `meta.json`; never re-ask.
- Always skip: every `generated-docs/` folder and its contents (tagged or not) · tagged generated docs elsewhere (`<meta name="generator">` content starting `darshan-singh-meel-docs`, or first-line comment starting `generated by darshan-singh-meel-docs` — v1 + v2) · any folder holding a `.generated-by-darshan-singh-meel-docs` marker · all `*-knowledge-graph/`, `knowledge-graph/`, `*-graphs/` · secret files · deps, build output (except dbt `target/manifest.json`, read by script), venvs, binaries · `analysis/`, `reviews/`.
- Git-ignored: per CLAUDE.md. Committed later → remove that line, say so. Outside repo → no change.
- Related → §8.

## 2. Sources
- Code only · code + docs · docs only (large PDF/Word/slide sets) — use what's there.
- Code = fact. Docs fill gaps (purpose, meaning, owners, decisions, processes) → `source: doc`.
- Conflict → keep both with evidence; code stays fact; node `conflict` + one line.
- Outranking docs → intended behaviour; code differs → `code differs from <doc>` (a finding).
- All conflicts in `index.md` → "Code vs docs".

## 3. Capture
Reference data: complete coverage, short summaries — every function, query, model, task, rule.
- **Points to code:** node → `path`, `line_start`, `line_end` (page/section for docs), one-line `summary`; functions + signature, params, return, calls/reads/writes. Edge → `evidence: "path:line"` of the exact line (call, `JOIN … ON`, `ref()`, `MERGE`). Pages cite `path:line` per step and rule.
- Unknown → `unclear`; deduced → `inferred`. Never invented.
- **Nodes:** repo · folder · file · module · function · class · endpoint · cli_command · ui_screen · job · dag · task · dbt_model · dbt_source · dbt_macro · dbt_test · table · view · column (key/important) · terraform_resource · storage_location · role · config · secret_ref (name only) · external_system · business_rule · flow · process · document · test_case · example_data
- **Edges:** contains · imports · calls · reads · writes · ref · fk · derived_from · depends_on · triggers · schedules · exposes · configures · deploys · grants · implements (code → rule) · documents (doc → anything) · part_of (step → flow) · illustrates (test/example → what it exercises)
- **Meaning:** flows (ordered steps) · logic (each business rule and non-trivial calculation in plain words + input → output) · processes (build, test, deploy, schedule, backfill, access — from CI files, Makefiles, READMEs, runbooks) · documents (summarised, linked) · tests/samples (`illustrates`, input → expected).
- **Data model** (docs draw ER from it): per table/view/stage/external/Iceberg/Delta → type · schema · grain · columns (type, nullable, meaning, sensitivity) · PK · relationships + cardinality · versioning (SCD2, `IS_CURRENT`) · partition/cluster · retention · written/read by · view sources + filter.
  - Find: DDL/migrations/Terraform → dbt (`manifest`, `schema.yml`; `unique`+`not_null` = PK, `relationships` = FK) → writes (`MERGE … ON`, `INSERT` lists, `QUALIFY … PARTITION BY`) → reads (`JOIN … ON`) → warehouse metadata (read-only, via notebook cells) → docs, fixtures.
  - Each key/relationship: `enforced` · `logical` · `inferred` + evidence. None → `unclear`.
- Structure, not data: names, types, keys, code — never rows/values (warehouse: metadata only).
- Never store: secret values, real personal data, large data samples.

## 4. Build
**Models:** Opus writes extraction scripts and does all understanding (parallel per folder for big repos) · Sonnet only runs Opus's scripts, writes files, checks paths — never interprets · never Haiku · graph review: separate Opus reviewer agent checks the builder's graph vs code before done (data model, flows, rules, ~20 random `path:line`); graph errors go back · no subagents → tell user to switch to Opus; already Opus without subagents → review as a separate second pass after the build, say so.

**Steps:** 1. Inventory (`.gitignore` + skip list). 2. Extract with scripts in `_scripts/` (Python `ast`, dbt: `dbt parse` only if user said yes, else existing `target/manifest.json` or parse `.sql`/`.yml`; Airflow DAGs, Terraform `.tf`, SQL DDL/`MERGE`/`JOIN`/`INSERT`, targeted search). Contract (§5 incremental): `_scripts/extract.py <repo> <out> [--files-from <list>]` → `<out>/graph/{nodes,edges}.jsonl`; hand-written inputs (summaries, flows, rules) read from its own folder, all in `_scripts/`; skips + prints entries whose ids are gone. `--files-from` (one path per line): only those files' nodes, folders they add, edges from/to them, meaning citing them · `_scripts/validate.py <repo> <graph>` → one coverage line. 3. Add meaning. 4. Write jsonl → pages → `index.md`, `README.md`, `meta.json`. 5. Validate: no absolute paths · every `path:line` real and matching · every edge resolves · no secrets · coverage (files mapped/total; nodes without evidence = 0).

**Layout**
```
<repo>-knowledge-graph/
  README.md          what, stats, last build
  index.md           start: one diagram (≤~7 boxes), entry points, Code vs docs
  meta.json          settings, commit, hashes, counts, generated_by
  graph/nodes.jsonl  {id, type, name, path, line_start, line_end, summary, tags, status}
  graph/edges.jsonl  {from, to, type, evidence, status}
  modules/ flows/ logic/ processes/ documents/
  data/model.json    entities, columns, keys, relationships, views
  data/model.md      Mermaid ER + views table
  answers/  _scripts/
```
- IDs stable, readable: `function:src/load.py:load_orders`, `dbt_model:fct_orders`.
- Every written file tagged generated (first-line comment in `.md`/`.html`; `generated_by` in `meta.json`). Never reads its own or any graph folder.

## 5. Keep it updated
`update.py` = `<skill>/references/update.py`, repo root, `python -I`. State in `meta.json` (`pending`, `docs_pending`) → nothing asked twice.
- Graph question (any skill): after commit(s), or task end with uncommitted only (options minus "next commit"). `update.py --dry-run` → follow `say`:
  - `ask` → one AskUserQuestion, no note in that reply: `<status>. Update the graph?` Update now in background (rec when task looks finished) · Wait — ask after the next commit · Wait until I say the work is done · No, skip.
  - Record: `update.py --choice now|next|done|skip`. next → ask after next commit · done → no asks; user says done → ask once (no `--dry-run`) · skip → no asks until updated; note shows growing count · now without background agents → say pending (note continues); switch to Opus.
  - `note` → no question, staleness line · `none` → nothing.
  - Other skills' graph setup answers → update first `--choice now` · as is `--choice skip`.
- Docs question: only after graph update finished; never with graph question, never mid-task (end of next reply). Worklist `docs_ask` true → one AskUserQuestion: `Graph updated (<one-line summary>). Update the docs that cover the changes: <worklist docs>?` Update now in background (rec) · Later · No.
  - Docs = tagged `darshan-singh-meel-docs` (v1/v2) or in marker folder, in `generated-docs/` (or shared, §8), citing changed lines/files/nodes or naming removed/changed things (`_spec/` excluded). Collect in `docs_pending` until refreshed.
  - Update now → background agent, docs skill, those docs only, no questions (docs-v2: own refresh steps) → `update.py --docs done` (`--docs done <doc> …` for some). One line when done.
  - Later → `--docs later` (ask after next graph update) · No → `--docs no` (ask only when an update adds docs). Both keep the note.
  - Docs built/refreshed in this task anyway → no docs question; `--docs done` after.
- Staleness note (`say` = `note`): `update.py --status` line, one line in Other findings, every repo reply. No question, never blocks; stops once updated.
  - Graph not updated: `Graph is N commits behind (M files) · docs K commits behind` (K from last docs refresh) · uncommitted only: `Graph is behind by M uncommitted files · docs behind` · no git: `… M changed files …`.
  - Graph updated, docs not: `Docs are N commits behind the graph (K docs)` · no commits to count: `Docs are behind the graph (K docs, U graph updates)`.
- Run (incremental, fast):
  1. `update.py`: change set (working tree vs `meta.commit` + untracked, renames, deletes; no git → hashes; secret files never read) → remap `path:line` of changed files in `_scripts/` inputs + pages (difflib, no LLM) → `_scripts/extract.py` → merge only what changed files own (their nodes + flows/rules/processes whose steps or edges cite them); unchanged lines byte-identical → `meta.json` → `_scripts/validate.py` → `_update/worklist.json`; previous state → `_update/prev/`. One line + time.
  2. Opus agent reads only worklist: `refresh` (new · changed + `was` · neighbour) · `moved` (refs already remapped) · `removed` · `renamed_ids` · `dangling_edges_dropped` · `meaning` (re-check; new functions → new rule/flow/command?) · `summaries` (repo, folders, `index.md` big picture) · `check_mentions` (unchanged hand-written files naming removed/changed things → Code vs docs) · `pages` (+ `index.md`) · `pages_new` · `pages_delete`. Fixes → hand-written `_scripts/` inputs, never only `graph/*.jsonl` → `update.py --redo` re-merges from `_update/prev/`.
  3. Graph review (separate Opus, §4) on worklist items; `validate.py` on whole graph.
  - Full rebuild only if asked · `full_rebuild_advised` (>half files, or `_scripts/*.py` changed). Huge change set → split worklist by folder, parallel Opus.
- Migrate pre-contract graph (`update.py` names the missing piece): `_scripts/extract.py` per §4 contract (wrap old extractor + merge steps) · `_scripts/validate.py` · `meta.json` `commit` (HEAD the graph matches) + `file_hashes` → `update.py --dry-run`.
- Rebuild never drops reasoned pages (`flows/`, `logic/`, `processes/`, `documents/`, `data/model.json`) → recreate or keep and re-verify.
- Counts recomputed from files every time, never from memory.

## 6. Answer
"What does X do end to end" · "how does upload work" · "what calls this procedure" · "what breaks if I change table Y".
- First question per session → one prompt, 2 questions, remembered (user may change anytime):
  - Answer from? Graph, confirmed in code (rec) · Code only · Graph + a folder I name. No graph: Build first (rec) · Code only · Code + folder.
  - Show as? On screen (rec) · Local HTML.
1. Find in graph: nodes, edges, pages; walk calls/reads/writes/ref/triggers.
2. Freshness vs `meta.json`: involved file hash unchanged → graph + open cited lines for key steps · changed → read that file's current code, graph as map, say so.
3. On screen: bullets + small diagram/call chain (`ui/upload.py:42 run_upload() → data.save_rows() → CALL SP_UPLOAD`), IN → OUT and `path:line` per step. HTML: `<graph folder>/answers/<slug>.html`, docs-skill style (components, `references/html-style.md`); give path; no graph → on screen only. Name sources; not found → "not found in repo".
4. Stale → after answering: graph question or staleness note, per `update.py --dry-run` `say` (§5). Never block on it.
- Models: Sonnet (simple lookups Haiku). Diagrams: Opus plans, Sonnet builds, Haiku checks layout.

## 7. After first build
One prompt: Documents (multi) Overview (rec) · Technical · User guide · None for now (overrides other picks); Format (multi) HTML (rec) · Markdown · Confluence → run docs skill with these + Graph = "Use as is" (it asks only the rest).

## 8. Related repos — one shared graphs folder
```
../<system-name>-graphs/
  <repo1>/   knowledge-graph/  generated-docs/
  <repo2>/   knowledge-graph/  generated-docs/
  _combined/ knowledge-graph/  generated-docs/   ← system graph
```
- Each repo graph = §1–7. `_combined` = thin system graph (underscore: on top, no name clash).
- Pointer per repo: `.knowledge-graph` (one line, relative path to its graph), git-ignored. Skills find the graph through it.
- Setup, one prompt, once (saved in each repo's and `_combined`'s `meta.json`):
  - Name: `<this repo>-system` (rec) · type one
  - Location: `../<name>-graphs/` (rec; outside repos → this one yes; local only) · other path
  - Existing (only if `./<repo>-knowledge-graph/` exists): Move into shared folder (rec) · Keep in repo, link · Rebuild there
  - Docs: Shared folder only (rec) · Shared + copy into each repo's `generated-docs/`
- Related repos lacking current graph → offer build/update (Opus, parallel, own setup).
- Shared folder outside repos: no `.gitignore`; local unless user makes it a repo.
- `_combined/knowledge-graph/`: `index.md` (system L0, unmatched calls) · `repos.json` (name → repo + graph paths relative to the shared folder, commit) · `meta.json` · `links.jsonl` (cross-repo only) · `flows/` · `data/model.json` · `answers/`.
- Links (Opus) by contract: HTTP routes ↔ client calls (+ base-URL config) · OpenAPI/gRPC/GraphQL · SQL procedures/tables/views ↔ calls/queries · topics · shared packages/schemas.
- Link: `{from: "web:src/api.ts:42", to: "api:routes/orders.py:18", type, contract: "POST /orders", status: matched|unmatched|inferred, evidence}`.
- Unmatched → `index.md`, noted not verified.
- Same rules: Opus + graph review, relative paths, no secrets, tagged.
- System graph updates only on request (`update.py` = one repo graph) → re-check only links touching that repo's worklist (`files`, `refresh`, `removed`) + `repos.json` commit → `_combined` docs citing them. Cross-repo questions → `_combined` → repo graphs → code.

## Report
**Graph review — output format.** Reviews the **graph**, not the code; never code-review wording (Approve, Must fix, Should fix).
```
Graph review — a second agent reviewed the graph built by the builder agent (checks the graph against the code; not a code review).
Checked: data model (N tables, N keys), N flows, N rules, N random path:line references
Result: N/N references correct · N graph errors found · N fixed · N still open
Fixed by the builder: <one line each: what in the graph was wrong → now correct>
Still open: <graph items marked unclear, if any>
```

Build summary, headings in order: Graph (path, git status) · Size and checks (counts by type, flows, conflicts) · Graph review (fixes) · Noticed while mapping (not verified; per Scope).
