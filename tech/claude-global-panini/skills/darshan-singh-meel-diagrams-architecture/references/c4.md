# C4 types: `c4-context`, `c4-container`, `c4-component`

The C4 levels from c4model.com. One spec shape for all three; the level decides which kinds are allowed and what the boundary means.

## Spec
```json
{"id": "booking-containers", "type": "c4-container", "title": "…", "key": "…", "notice": "…",
 "groups": [{"id": "platform", "label": "Booking platform"}],
 "nodes": [{"id": "api", "label": "booking-api", "kind": "container", "tech": "Python, FastAPI",
            "desc": "Search, holds, bookings", "group": "platform"},
           {"id": "psp", "label": "Payment provider", "kind": "system", "external": true, "desc": "Card payments"}],
 "edges": [{"from": "api", "to": "psp", "label": "Charges card", "tech": "REST"}]}
```

| Field | Rule |
|---|---|
| node `kind` | context: `person`, `system` · container: + `container`, `database`, `queue` · component: + `component` |
| node `external` | `true` for people or systems outside the scope (grey, tag "[External …]") |
| node `desc` | required: one short line of responsibility (C4: every element has a short description) |
| node `tech` | required for `container`, `database`, `queue`, `component` (C4: every container and component names its technology); drawn as `[Container: tech]` |
| node `group` | the boundary id; omit for elements outside it |
| `groups` | context: optional enterprise boundary · container: one `Software System` boundary (required) · component: one `Container` boundary (required); `kind` overrides the bracket word |
| edge `label` | required: what the line does ("Charges card"); "Uses", "Calls", "Reads", "Sends", "Talks to" alone are rejected |
| edge `tech` | protocol; drawn as `label [tech]`; label plus tech ≤ 36 characters; required between two containers, databases or queues |
| also | `rank`, `dim`, `href`, `tip` on nodes; `style`, `from_side`, `to_side` on edges; `direction`, `max_w` |

- Default ranks when no node sets `rank`: people and externals that send anything in at the entry side, externals that only receive at the far side, the rest by flow. Set `rank` on every node to override.
- The engine tries the default layout, then sends one or two crowded or defective arrows out of another side (`from_side`) and keeps the cleanest; a `from_side` in the spec is never changed.

- Style: `plain` only. C4 has its own notation; `dbt` / `airflow` are rejected.
- Look: person = stick figure · system in scope = dark box · container / database / queue = blue box / cylinder / pill · component = teal · external = grey · boundary = grey dashed frame. C4 prescribes no colours; this mapping is ours and the legend names it.
- Mermaid: native `C4Context` / `C4Container` / `C4Component` with `Person`, `System`, `Container`, `ContainerDb`, `ContainerQueue`, `Component`, `_Ext`, `System_Boundary`, `Container_Boundary`, `Rel(from, to, label, tech)`. Mermaid lays C4 out itself; the SVG is the reference picture.

## Which level
| Level | Scope | Primary elements | Audience | Draw it |
|---|---|---|---|---|
| context | one software system | the system, its people, external systems | everyone, technical or not | always |
| container | one software system | apps and data stores inside it | architects, developers, ops | always |
| component | one container | components inside it, plus the containers and systems they touch | architects, developers | only when it adds value |

## Rules
- One level per diagram; never mix components of two containers.
- Every line is one direction; a two-way exchange is two lines with two labels.
- Only direct relationships of the elements in scope; second-hop systems go in their own diagram.
- Deployment (where containers run) is the `deployment` type, not a C4 level here.
