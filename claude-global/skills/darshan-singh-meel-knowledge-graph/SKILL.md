# Knowledge Graph

A detailed, verifiable map of the repo. Answers, docs, and reviews are built on it — **if the graph is wrong, everything is wrong**, so accuracy comes first. Global rules in CLAUDE.md apply (relative paths, data handling, local files only).

## Scope — mapping only
- Building or updating the graph **maps what the code does**. It is not a code review: don't hunt for bugs, investigate, confirm, measure impact, or run the app to test suspicions.
- Something looks wrong while mapping → record it as a `possible_issue` note on the node (one line + `path:line`), mark it **not verified**, and move on.
- Report back: only a count and up to 5 one-liners (dead code, cycles, unused models, possible bugs) under **Noticed while mapping (not verified)**, then one line: "Run a review to check these" (`darshan-singh-meel-review`). Never "confirmed bugs", severity, or impact numbers.

## 1. Setup — first build only
Graph already exists (`./<repo>-knowledge-graph/`, or the path in `./.knowledge-graph`) → skip this and go to section 5 (update), using the saved settings.

Silently list the doc files found (relative paths, by folder). Then **one AskUserQuestion prompt, 4 questions:**

| Header | Question | Multi | Options (first = recommended) |
|---|---|---|---|
| Location | Where should the graph go? | no | `./<repo>-knowledge-graph/`, git-ignored (Recommended) · Same folder, committed to git · Another path |
| Doc sources | Which docs should I read? | yes | Hand-written docs: READMEs, specs, runbooks (Recommended) · Everything · Let me pick what to skip · Code only |
| Priority | Should any docs outrank the code? | no | No — code is the source of truth (Recommended) · Yes, I'll pick them (approved specs, contracts, regulations) |
| Related repos | Are other repos related (e.g. a web app that calls this API)? | no | No (Recommended) · Yes, I'll give their paths |

- Save all answers in `meta.json` and never ask again.
- **Always skipped, whatever is chosen:** every `generated-docs/` folder (in this repo and in the shared graphs folder) and anything in it, tagged or not; generated docs anywhere else (a `<meta name="generator">` whose content starts with `darshan-singh-meel-docs`, or a first-line comment starting `generated by darshan-singh-meel-docs` — covers v1 and v2), any folder holding a `.generated-by-darshan-singh-meel-docs` marker file, every `*-knowledge-graph/`, `knowledge-graph/`, and `*-graphs/` folder, secret files, dependencies, build output (except dbt `target/manifest.json`, read by script), virtualenvs, binaries, `analysis/`, `reviews/`.
- **Git-ignored:** per CLAUDE.md. Committed later → remove that line and say so. Outside the repo → no change.
- Related repos = yes → section 8.

## 2. Source priority
- Sources can be code only, code + docs, or docs only (e.g. a large PDF/Word/slide set).
- **Code wins:** what the code actually does is the fact.
- **Docs fill gaps:** purpose, business meaning, owners, decisions, processes — tagged `source: doc`.
- **Conflicts are never hidden:** record both sides with evidence, keep the code as the fact, mark the node `conflict` with one line.
- **Docs that outrank code** (chosen in setup): treated as intended behaviour; where code differs, mark `code differs from <doc>` so it surfaces as a finding.
- All conflicts listed in `index.md` under "Code vs docs".

## 3. What to capture
Reference data, not a deliverable: **complete coverage, short summaries.** Capture every function, query, model, task, and rule — not just the main ones.

**Every item points to the code**
- Node: `path`, `line_start`, `line_end` (page/section for documents), one-line `summary`; functions also signature, params, return, and what they call/read/write.
- Edge: `evidence: "path:line"` — the exact line that creates it (the call, `JOIN … ON`, `ref()`, `MERGE`).
- Flow, logic, and data pages cite `path:line` for every step and rule.
- Unknown → `unclear`; deduced → `inferred`. Never invented.

**Node types:** repo · folder · file · module · function · class · endpoint · cli_command · ui_screen · job · dag · task · dbt_model · dbt_source · dbt_macro · dbt_test · table · view · column (key/important) · terraform_resource · storage_location · role · config · secret_ref (name only) · external_system · business_rule · flow · process · document · test_case · example_data

**Edge types:** contains · imports · calls · reads · writes · ref · fk · derived_from · depends_on · triggers · schedules · exposes · configures · deploys · grants · implements (code → rule) · documents (doc → anything) · part_of (step → flow) · illustrates (test/example → what it exercises)

**Meaning, not just structure**
- **Flows:** end-to-end paths as ordered steps ("file lands → load → dbt → dashboard").
- **Logic:** every business rule and non-trivial calculation in plain words, with input → output.
- **Processes:** build, test, deploy, schedule, backfill, access — from CI files, Makefiles, READMEs, runbooks.
- **Documents:** non-code files summarised and linked to what they describe.
- **Test cases and sample files:** linked (`illustrates`) to what they exercise, with input → expected output — docs reuse them as examples.

**Data model** — every table, view, stage, external/Iceberg/Delta table, so docs can draw an ER diagram straight from the graph:
- Per object: name · type · schema · **grain** · columns (type, nullable, meaning, sensitivity) · **primary key** · **relationships** (columns, cardinality) · versioning (SCD2, `IS_CURRENT`) · partition/cluster keys · retention · written/read by · for views: sources and filter.
- Find it, best first: DDL and migrations (incl. Terraform) → dbt (`manifest.json`, `schema.yml`, tests: `unique`+`not_null` = PK, `relationships` = FK) → code that writes (`MERGE … ON`, `INSERT` lists, `QUALIFY … PARTITION BY`) → code that reads (`JOIN … ON`) → warehouse metadata (read-only, via notebook cells — `darshan-singh-meel-notebook`) → docs and fixtures.
- Every key/relationship: `enforced`, `logical`, or `inferred`, with evidence. No evidence → `unclear`.

- **Structure, not data:** the graph records names, types, keys, and code — never data rows or values (warehouse metadata only: names, types, tags).
- **Never store:** secret values, real personal data, or large data samples.

## 4. Build
**Models — accuracy first**
- **Opus:** writes the extraction scripts and does all reading and understanding — summaries, calls, flows, rules, processes, data model. Large repos: parallel Opus subagents per folder.
- **Sonnet:** mechanical only — runs Opus's scripts, writes files from Opus's results, path checks. Never decides what code means.
- **Never Haiku** for building or updating.
- **Graph review:** a separate Opus reviewer agent checks the builder's graph against the code before it's done — data model, flows, rules, ~20 random `path:line` references. Graph errors go back to the builder. Format under Report back.
- No subagents → tell the user to switch to Opus (`/model`) before building.

**Steps**
1. Inventory files (respecting `.gitignore` and the skip list).
2. Extract structure with scripts: Python `ast`; dbt (`dbt parse` only if the user said yes; else existing `target/manifest.json`, or parse `.sql`/`.yml`); Airflow DAG parsing; Terraform `.tf`; SQL objects, keys, and columns from DDL/`MERGE`/`JOIN`/`INSERT`; targeted search for other languages. Save scripts in `_scripts/` so updates can rerun them.
3. Add meaning: flows, rules, data model, processes, documents, test cases.
4. Write `graph/*.jsonl`, then the pages, then `index.md`, `README.md`, `meta.json`.
5. Validate: no absolute paths; every node and edge has a real, matching `path:line`; every edge points to an existing node; no secrets. Report coverage (files mapped / total; nodes without evidence = 0).

**Folder layout**
```
<repo>-knowledge-graph/
  README.md            what this is, stats, last build
  index.md             start here: one big-picture diagram (≤ ~7 boxes), entry points, "Code vs docs"
  meta.json            settings, commit, file hashes, counts, generated_by tags
  graph/nodes.jsonl    {id, type, name, path, line_start, line_end, summary, tags, status}
  graph/edges.jsonl    {from, to, type, evidence, status}
  modules/  flows/  logic/  processes/  documents/    one page each
  data/model.json      entities, columns, keys, relationships, views
  data/model.md        Mermaid ER diagram + views table
  answers/             local HTML answers (section 6)
  _scripts/            extraction scripts
```
- IDs are stable and readable: `function:src/load.py:load_orders`, `dbt_model:fct_orders`.
- Every file the graph writes is tagged generated (first-line comment in `.md`/`.html`; `generated_by` in `meta.json`).
- The graph never reads its own folder or any other graph folder.

## 5. Keep it updated
- **After any change or commit** in the repo (any skill, any task), end with one line:
  `Graph and docs are out of date for N files — reply "go" to update both in the background, "graph" for the graph only, or "no".`
  - Docs = only files tagged `darshan-singh-meel-docs` in this repo's docs folder (`./generated-docs/`, or the shared one when section 8 applies) that cover the changed files; none → offer the graph only (`"go"` or `"no"`).
  - **go** → background Opus agent updates the graph, then the docs skill refreshes the affected sections of those docs (same documents and formats, no setup questions). One line when done.
  - **graph** → graph only. **no** → fine; don't ask again for the same changes.
  - No background agents → say it's pending; switch to Opus to update.
- **Incremental:** changed files from `git diff <meta.commit>` plus `git status --porcelain` (new files), or hashes → remove their nodes/edges, re-extract, refresh affected pages and `index.md` → rerun step-5 validation on the whole graph and the graph review on the changed nodes. Full rebuild only if asked or more than half the files changed.
- **Rebuilds never lose content:** pages written by reasoning (`flows/`, `logic/`, `processes/`, `documents/`, `data/model.json`) are re-created from the sources or kept and re-verified — never silently dropped.
- **Counts come from the files,** recomputed after every build or update — never from memory.

## 6. Answer questions
Any question about the repo: "what does X do end to end", "how does the upload work", "which function calls which procedure", "what breaks if I change table Y".

**First question in a session — one prompt, 2 questions, then remember the answers:**
- **Answer from?** Graph, confirmed in code (Recommended) · Code only · Graph + a folder I name. No graph: Build the graph first (Recommended) · Code only · Code + a folder I name.
- **Show as?** On screen (Recommended) · Local HTML page.
- The user can change either anytime ("answer from code", "show as HTML").

**How**
1. **Find it in the graph:** search nodes, edges, and pages; walk `calls` / `reads` / `writes` / `ref` / `triggers`.
2. **Check freshness:** compare involved files with `meta.json`. Involved files' hashes unchanged → answer from the graph, opening the cited lines for key steps. Changed → read that file's current code, using the graph as a map, and say so in one line.
3. **Answer:**
   - On screen: short bullets + a small diagram or call chain (`ui/upload.py:42 run_upload() → data.save_rows() → CALL SP_UPLOAD`), with IN → OUT and `path:line` per step.
   - HTML: `<graph folder>/answers/<question-slug>.html`, in the docs skill's style and components. Give the path. No graph → on screen only.
   - Say which sources were used. Not found → "not found in repo".
4. **Graph was out of date:** after answering, offer once with the same one-word reply (section 5). Never block the answer on it.

**Models:** answers on Sonnet (simple lookups on Haiku). Diagrams: Opus plans, Sonnet builds, Haiku checks layout.

## 7. After the first build — offer docs
One prompt: **Documents** (multi) — Overview (Recommended) · Technical · User guide · None for now (overrides other picks); **Format** (multi) — HTML (Recommended) · Markdown · Confluence. Then run `darshan-singh-meel-docs` with these answers and the graph as the source (Graph = "Use as is"; it asks only what's left).

## 8. Related repos — one shared graphs folder
With related repos (e.g. web → API → DB), every graph and every generated doc lives in **one shared folder next to the repos**:
```
../<system-name>-graphs/
  <repo1>/   knowledge-graph/   generated-docs/
  <repo2>/   knowledge-graph/   generated-docs/
  _combined/ knowledge-graph/   generated-docs/     ← system graph across all repos
```
- Each repo's `knowledge-graph/` is a normal repo graph (sections 1–7). `_combined/` is the thin system graph below. The underscore keeps it on top and can't clash with a repo name.
- **Pointer in each repo:** a one-line file `.knowledge-graph` holding the relative path to its graph (e.g. `../orders-platform-graphs/web/knowledge-graph`), added to `.gitignore`. Every skill finds the graph through it.

**Setup — one prompt, asked once (saved in every repo's `meta.json` and `_combined/knowledge-graph/meta.json`)**
| Header | Question | Options (rec first) |
|---|---|---|
| Name | Name for the shared folder? | `<this repo>-system` (rec) · I'll type one |
| Location | Where should it go? | `../<name>-graphs/` next to the repos (rec; outside the repos, so this one yes is needed; local only) · Another path |
| Existing | This repo already has `./<repo>-knowledge-graph/` — what should I do? (only if one exists) | Move it into the shared folder (rec) · Keep it in the repo, link to it · Rebuild in the shared folder |
| Docs | Where should generated docs go? | Shared folder only (rec) · Shared folder + copy each repo's docs into that repo's `generated-docs/` |
- Related repos without a current graph → offer to build/update them first (Opus, in parallel, each with its own setup answers).
- The shared folder is outside every repo: no `.gitignore` there; local only unless the user asks to make it its own repo.

**`_combined/knowledge-graph/` contents**
```
  index.md          L0 of the whole system; unmatched calls
  meta.json         settings, commits used
  repos.json        repo name → repo path and graph path (relative to the shared folder), commit used
  links.jsonl       cross-repo edges only
  flows/            end-to-end flows across repos
  data/model.json   combined data model + cross-repo relationships
  answers/          cross-repo answers
```
- **Cross-repo links (Opus):** match contracts — HTTP routes ↔ client calls (incl. base-URL config), OpenAPI/gRPC/GraphQL, SQL procedures/tables/views ↔ calls and queries, message topics, shared packages and schemas.
- Each link: `{from: "web:src/api.ts:42", to: "api:routes/orders.py:18", type, contract: "POST /orders", status: matched | unmatched | inferred, evidence}`.
- **Unmatched calls** (a route no repo defines, a procedure nobody calls) listed in `index.md` — noted, not verified (mapping only).
- Same rules as repo graphs: Opus builds, graph review, relative paths, no secrets, tagged generated.
- **Updates:** when a repo's graph updates, re-check only that repo's cross-repo links (same one-line offer).
- **Questions that cross repos:** `_combined` graph → repo graphs → code.

## Report back
**Graph review — output format.** Reviews the **graph**, not the code; never code-review wording (Approve, Must fix, Should fix).
```
Graph review — a second agent reviewed the graph built by the builder agent (checks the graph against the code; not a code review).
Checked: data model (N tables, N keys), N flows, N rules, N random path:line references
Result: N/N references correct · N graph errors found · N fixed · N still open
Fixed by the builder: <one line each: what in the graph was wrong → now correct>
Still open: <graph items marked unclear, if any>
```

**Build summary** — headings in this order: Graph (path, git status) · Size and checks · Graph review (the second agent's fixes) · Noticed while mapping (not verified).
- Path, node/edge counts by type, flows found, conflicts count, `.gitignore` status.
- Noticed while mapping (not verified): per Scope.
